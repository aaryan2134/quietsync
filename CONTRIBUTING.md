# Contributing

Thanks for helping. This file covers how to get set up, what we expect in a PR, and where the sharp edges are. How decisions get made is in [GOVERNANCE.md](GOVERNANCE.md).

## Setup

Use [Bun](https://bun.sh) 1.4.4, pinned in `.bun-version` and `package.json`, and Node 22+ (the plugin runs on it). Earlier Bun versions cannot read the current lockfile format.

```sh
bun install --frozen-lockfile
bun run typecheck
bun run build        # bundles packages/cli/dist and copies it into plugins/claude-code/dist
bun test             # unit, relay end-to-end, and bridge tests (the bridge test needs the build)
node --test scripts/test/*.test.mjs  # dependency-free smoke checks of the shipped bundle and client configs
```

Try your changes in Claude Code without installing anything:

```sh
QUIETSYNC_HOME=/tmp/al-me claude --plugin-dir ./plugins/claude-code --plugin-dir ./plugins/claude-code-ui
```

Run a second session with another `QUIETSYNC_HOME` and a local relay (`bun packages/cli/dist/quietsync.mjs relay`) to test two people on one machine.

## Repository layout

| Path | Purpose |
|---|---|
| `packages/core/src` | Protocol, cryptography, policy, profiles, scanning, guards and the per-session runtime |
| `packages/relay/src` | WebSocket relay |
| `packages/cli/src` | CLI, MCP bridge, tools and hooks |
| `plugins/claude-code` | Claude Code plugin; `dist/` is generated by `bun run build` |
| `plugins/claude-code-ui` | Claude Code UI integration |
| `docs/` | Architecture, protocol, security, policy, profiles, relay, safety, testing and audit guides |

## What a good PR looks like

- one change, described in a sentence or two: what and why
- tests next to the change:
  - logic in `packages/core` gets a unit test in `packages/core/test/core.test.ts`
  - anything on the wire or between two people gets an end-to-end test in `packages/relay/test/e2e.test.ts`
  - anything in the bridge, hooks or tool gate gets a case in `packages/cli/test/bridge.test.ts`
- `bun run typecheck`, `bun run build` and `bun test` pass, and `bun audit` and `gitleaks detect --no-git --source .` are clean (CI runs both, plus CodeQL)
- user-facing changes add a line to [CHANGELOG.md](CHANGELOG.md)
- docs updated when behavior changes (`docs/`, `SETUP.md`, the skill in `plugins/claude-code/skills`)
- commits signed off for the [DCO](https://developercertificate.org/): `git commit -s`

If your change touches delivery into a session or the approval gate, also do a manual two-session check and say what you saw in the PR.

## Security-sensitive code

These paths follow the independent review requirements and current maintainer stage in [GOVERNANCE.md](GOVERNANCE.md). The multi-maintainer target is two approvals, one from a maintainer (see [.github/CODEOWNERS](.github/CODEOWNERS)):

- `packages/core/src/{crypto,envelope,policy,rules,policies,guard,dlp,sanitize,frame,node,team}.ts`
- `packages/cli/src/{bridge,hook,ipc}.ts`, `packages/cli/assets/hook.sh`
- `plugins/*/hooks/`

Rules of thumb there:

- never let the model hold a capability the human didn't grant in a UI the model can't drive
- whatever the human approves must be byte for byte what's sent; route all outgoing text through `prepareOutbound`
- fail closed: if a check can't run, refuse or hold, don't allow
- a peer-controlled string that reaches the model goes through `sanitizeInbound`/`sanitizeLabel` and, if it's longer than a label, inside a fence
- if you change a guarantee, update [docs/security.md](docs/security.md) in the same PR

Found a vulnerability? Don't open an issue; follow [SECURITY.md](SECURITY.md).

## RFCs

Protocol changes, security model changes, new public interfaces and new adapters start as an RFC in [rfcs/](rfcs/README.md). Small, compatible additions (an optional payload field, a new scanner rule) can skip it if a maintainer agrees on the issue.

## Adapters

New agents go in `plugins/<agent>` and reuse the bridge (`quietsync mcp`) and its control socket. They must meet the requirements in [docs/adapters.md](docs/adapters.md) before they're merged.

## Style

- TypeScript, strict, ESM, no default exports. The CLI and bridge must run on Node 22+ and Bun, so only `node:` APIs outside the relay.
- No new runtime dependencies without discussion. Crypto stays on `@noble`.
- Comments say why, not what, and only where it isn't obvious.
- User-facing text is short and plain: say what happened and what to do. No exclamation marks, no jargon the user didn't introduce.
